# 未来路线图

[English](future-roadmap.md) | 简体中文

本文描述 Long Task Manager 在 MVP 之后的演进。标记为“已交付”的章节说明已经实现的能力；后续阶段仍是没有固定时间表的提案。

## 长期架构

长期方向围绕三层展开：

```text
规划与策略引擎
      ↓
执行与状态管理层
      ↓
数据与知识底座
```

### 规划与策略引擎

规划层负责将长期目标转换为可执行、可审核的结构。

潜在能力包括：

- 独立的工作分解结构（WBS）规划树（已在 v0.3 交付）
- 带明确标准且状态由节点派生的里程碑（已在 v0.3 交付）
- 基于历史执行数据进行时间估算
- 项目缓冲和供给缓冲，用于吸收计划偏差
- 根据审核结果和进度反馈重新计算优先级

### 执行与状态管理层

执行层负责将计划转换为可持续的行动，同时保留人工控制能力和故障恢复能力。

潜在能力包括：

- 定期递归复盘，对照初始目标与当前进展
- 资源感知的调度与瓶颈预警
- 根据依赖关系、可用容量和返工概率提供并行度建议
- 对高影响状态转换设置审批关卡
- 用可解释建议替代不透明的自动重新排序

### 数据与知识底座

数据底座负责让执行历史能够反哺未来规划。

潜在能力包括：

- 任务和步骤的计划时长与实际时长
- 资源日历与技能画像
- 延迟原因、审核结果和返工历史
- 项目级记忆与复盘记录
- 健康度、风险和缓冲消耗指标

## 建议演进路线

### v0.2 — 递归复盘与进度偏差（已交付）

**目标：** 建立从执行历史反馈到规划调整的第一条闭环。

已交付范围：

- 手动创建任务进度复盘，并由用户填写预期完成百分比
- 保存标准实际进度快照，以 ±5 个百分点为阈值分类为 `ahead`、`on_track` 或 `behind`
- 根据步骤和运行历史生成确定性的事实依据与建议
- 通过 `previous_review_id` 形成递归历史
- 每条复盘记录一次明确的 `keep_plan` 或 `adjust_plan` 决策
- 写入时间线和任务日志审计事件

首版有意不自动安排复盘、不估算时间、不调用 LLM 分析，也不自动执行建议；这些能力需要进一步定义规划、调度和审批语义。

### v0.3 — WBS 任务树与里程碑（已交付）

**目标：** 在不扩展或改变可执行 Step 图的前提下，增加多层级规划结构。

已交付范围：

- 独立 WBS 节点、稳定深度优先顺序，以及到执行 Task 的可选唯一关联
- 里程碑标题和标准，其只读状态由所属节点派生
- 确定性的直接子节点汇总，排除 inactive、archived、cancelled 和不可报告工作
- 同根无环依赖、blocked 状态派生和最长未完成依赖链提示
- 子节点与依赖变更的不可变 draft proposal，支持一次性批准/拒绝和根版本冲突检查
- 独立 API、任务详情 UI、时间线事件、SQLite 迁移支持和回归测试

本版本有意不加入估时、截止时间、资源调度、自动重排、LLM 关键路径推理或跨根依赖。

### v0.4 — 时间估算与项目缓冲

**目标：** 让计划偏差可见且可管理，而不是隐藏在固定截止时间中。

潜在范围：

- 相似任务的历史时长分布
- 保守估算与激进估算
- 项目缓冲与供给缓冲
- 缓冲消耗报告
- 基于历史偏差的调度建议

**原则：** 时间估算应先作为可解释建议，不应静默覆盖用户承诺，也不应制造虚假的精确度。

### v0.5 — 资源日历、技能与瓶颈

**目标：** 将任务匹配给合适的可用能力，而不是简单分配给看起来最空闲的人。

潜在范围：

- 资源可用性日历
- 技能与熟练度画像
- 工作负载和利用率摘要
- 容量受限时的瓶颈预警
- 重新分配或调整顺序的建议

**原则：** 先提供可见性和建议。自动重新分配必须经过明确审批。

### v0.6 — 并行度与返工决策

**目标：** 帮助用户在完全并行和部分串行之间做出选择。

潜在范围：

- 依赖感知的并行度分析
- 考虑容量的完成时间估算
- 返工概率信号
- 并行计划与串行计划对比
- 由人工审批执行策略变更

本阶段建立在现有并行步骤变体和对比组之上，不替换它们。

### v0.7 — 进度热力图与风险可观测性

**目标：** 让长时间工作能够一眼看懂。

潜在范围：

- 里程碑健康度指标
- 风险与延期热力图
- 步骤、任务和项目趋势视图
- 缓冲与工作负载可视化
- 可解释的状态转换和下一步建议

界面应说明某个项目健康、有风险或延期的原因，而不能只依赖颜色。

### v0.8 — 专注工作区

**目标：** 支持个人专注执行，但不把系统变成通知过多的生产力工具集合。

潜在范围：

- 当前步骤的专注执行工作区
- 可选的专注计时器或番茄钟会话
- 抑制非紧急的应用内通知
- 清晰区分专注状态与工作流状态

专注功能应保持可选，不能隐藏紧急审批、失败或安全事件。

## 硬规则与软引导

系统应将可强制执行的工作流规则与可解释的建议结合起来。

### 硬规则

- 已定义状态转换的审批要求
- 依赖约束
- 合法的任务、步骤和运行状态转换
- 保留历史运行记录和决策
- 外部执行集成的安全边界

### 软引导

- 时间和资源估算
- 瓶颈预警
- 优先级建议
- 递归复盘提醒
- 并行度与返工建议

建议应公开其输入和推理依据，让人可以接受、修改或拒绝。

## 非目标

本路线图不承诺立即支持：

- Claude 执行或通用 CLI Agent 执行
- 不受限制的 shell 执行
- 多租户身份与授权
- 计费
- 完整的企业级项目管理套件
- 不透明的自主重新排序

当前实现仍然是已支持行为的唯一事实来源。未来路线图中的项目只有在数据模型、API 行为、安全边界、测试和用户体验都定义清楚后，才应纳入已实现范围。
