# Product Brief

## 产品目标

Long Task Manager 是一个面向长时间任务的管理系统。

它的目标不是替代执行者，而是让用户能够以自然对话方式发起任务，并在任务持续推进的过程中持续管理步骤、执行尝试、审批、产物和事件。

## 目标体验

用户可以像聊天一样创建任务。

任务创建后即成为 `Task`，初始状态可以是 `status=intake`，而不是先进入额外的前置任务实体。

系统应支持以下核心体验：

- 用户可以像聊天一样创建任务
- 任务可以被拆成多个 step
- 每个 step 可以多次执行
- 每次执行都有独立 run 记录
- 用户可以审核、打回、重跑
- step 可以在执行中途动态增加
- step 可以 fork 成并行方案
- 系统记录产物、事件和进度

## 关键产品原则

### 1. 任务优先，创建即归属 Task

任务从创建开始就是 `Task`。

系统可以区分任务所处阶段，例如：
- `intake`
- `planning`
- `in_progress`
- `blocked`
- `done`

任务创建后即进入 `Task.status=intake`，对话输入直接归属 Task，不设置额外的前置任务实体。

### 2. Step 是可演化结构，不是固定清单

任务步骤不是一次生成后不可变化的固定数组。

系统必须支持：
- 动态新增 step
- 插入 step
- 跳过 step
- 用新 step 替代旧 step
- fork 成并行 variants
- 复制子步骤树
- 对比多个 variants
- 选择最终 variant 进入主线

### 3. 运行记录比最终结果更重要

Step 不保存唯一执行结果。

每次执行都形成独立 `StepRun`，用于保留：
- 输入
- 输出
- 状态
- 执行者
- 审核结论
- 产物
- 耗时

历史 run 必须完整保留，不能被覆盖。

### 4. 流程管理与执行解耦

系统负责管理流程，不替代执行工具。

外部执行者可以是：
- `human`
- `agent`
- `worker`
- `system`

Codex、CLI、browser、database、file 等都不是任务领域中的执行者类型，而是能力实现层的细节。

### 5. 能力调用可审计

系统需要记录每次能力调用，用于追踪：
- 调用了什么能力
- 由谁发起
- 通过哪种 adapter 实现
- 输出了什么
- 是否失败
- 产生了哪些产物

## 成功标准

如果 MVP 成功，用户应该能够：
- 通过对话创建一个长期任务
- 看到任务被拆解为可执行步骤
- 对某一步进行多次运行与重跑
- 对结果进行审核与打回
- 在过程中新增步骤或分叉并行方案
- 查看完整时间线、产物和结构化下一步动作
